# Evidence standings and calibration

Use the shared structured report contract. Every central claim needs a short,
exact quote at a valid repository-relative path/line range; give multiple sources
when a relationship requires both caller and implementation. A quote establishes
what the source says, not automatically whether your architectural interpretation
is true. Do not cite this methodology as evidence about the surveyed project.

- observed: source/configuration directly demonstrates the stated relationship;
  describe it as source evidence, not execution or live deployment observation.
- inferred: plausible interpretation with evidence and remaining alternatives.
- unknown: uninspected, missing or runtime/intent evidence unavailable. State what
  would settle it rather than inventing a probability or asking factual trivia.

Keep system shape, data flow and declared deployment distinguishable. An as-built
shortcut is observed; calling it accepted debt or a mandated boundary requires
intent evidence. Do not mark an assumption confirmed without user calibration.

Ask at most three consequential intent questions: whether a bypass is deliberate,
which owner should guide future reviews, or whether a duplicated concept is meant
to remain separate. Explain why the answer matters. Resolve cheap source facts
and stale-doc discrepancies yourself. No unsupported recommended answer should
be presented as the user's established intent.

The final proposal is compact, current and explicit about exclusions. It is not
a file inventory, task history, new ADR or automatically accepted baseline.
